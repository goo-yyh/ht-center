# 海天智能寻源 Demo 实施与设计方案

## 1. 文档信息

- 文档编号：0003
- 文档类型：实施与设计方案
- 产品基线：**specs/0002_simple.md**
- 实施范围：智能寻源管理端、内部供应商 Demo、外部供应商 Demo、共享数据库、DeepSeek Agent
- 目标：在不扩张为完整采购平台的前提下，形成可真实操作、可持久化、可重复初始化、可跨三个系统演示的寻源闭环

### 1.1 变更覆盖说明

本方案已经按最新产品规则更新，以下规则优先于旧版本设计和历史实现命名：

1. 采购端在 RFQ `OPEN` 阶段即可查看每家供应商的最新报价，不存在停止后才开放内容的产品步骤。
2. 内部供应商对同一询价只能提交一版正式报价。
3. 外部供应商首版报价后获得一份基于本次提交时有效报价的 `HIGH`、`MEDIUM` 或 `LOW` 竞争力分析，并且仅允许再提交一版，因此最多两版。
4. 报价历史不可覆盖；Agent 评估、中选和 PR 始终使用停止报价时每家供应商的最新有效版本。
5. 到期或提前停止只关闭后续报价，不改变报价内容的可见性。
6. 文档中保留的 **quote_sealed_payloads**、**revealed_quote_details**、revealedAt、`QUOTE_SEAL_KEY_V1` 或相关旧名称，只是数据库升级和旧客户端兼容说明，不是现行需求。

## 2. 方案结论

本期采用以下明确方案：

1. 保留现有 **haitian** Next.js 项目，继续使用 **/agents/sourcing** 作为智能寻源管理入口。
2. 新建内部供应商和外部供应商两个独立 Next.js 项目。
3. 不新增第四个独立后端服务；唯一核心业务 API 放在现有 **haitian** 项目中。
4. 三个应用都具备 Next.js 服务端能力，但只有核心业务 API 可以直接访问 PostgreSQL 和 DeepSeek。
5. 两个供应商应用通过自己的 Route Handler 作为 BFF，服务端调用核心业务 API；浏览器不跨域直连核心 API。
6. PostgreSQL 是唯一业务数据源。页面常量、React State 和 localStorage 不能保存正式业务状态。
7. 使用真实 DeepSeek API，但供应商筛选、金额计算、状态流转、中选和 PR 创建由服务端规则控制。
8. 报价采用版本化明细：采购端与 Agent 在 RFQ `OPEN` 时即可读取每家供应商最新报价；内部供应商最多一版，外部供应商最多两版并获得竞争力分析。
9. Demo 初始化时写入五条完整场景；初始化幂等，重置事务化，三个应用共享同一版本数据。
10. 本期默认以本地三应用联调和现场演示为交付目标，同时保留部署到无状态平台的配置方式。
11. 现有 **haitian** 项目是唯一 UI 视觉基线；管理端直接复用现有后台壳，两个供应商端共享同一套主题、字体、圆角、间距、状态色和交互反馈。
12. 外部供应商从统一注册页直接提交简化资料，不生成专属注册链接或注册邀请 Token；注册完成后仍然只能查看原供应商已经受邀的 RFQ。

## 6. 系统调用边界

### 6.1 唯一核心业务 API

核心业务 API 位于 **apps/sourcing-center/app/api/demo/v1**。以下能力只能由它执行：

- 读取和写入 PostgreSQL。
- 生成业务编号。
- 校验状态转换。
- 创建 RFQ、邀请和模拟通知。
- 接收并保存报价版本、计算外部供应商竞争力、停止后续报价。
- 调用 DeepSeek。
- 计算报价排名。
- 创建唯一中选和 PR。
- 初始化、完整性检查和重置。

### 6.2 供应商端 BFF

供应商浏览器只访问本项目的同源 Route Handler。外部供应商的统一注册页是唯一无需供应商会话的入口：浏览器只提交联系人、邮箱和密码，外部 BFF 在服务端固定绑定 **EXT-SUP-DEMO-004**，再调用核心注册接口；浏览器不能传入或切换 supplierId。

除统一注册页外，供应商 BFF 在服务端：

1. 读取签名 HttpOnly Cookie 中的演示供应商身份。
2. 使用只存在于服务端的服务凭证调用核心业务 API。
3. 转发允许返回给当前供应商的 DTO。
4. 不缓存正式业务写入结果。

浏览器不得直接携带 **supplierId** 或 **role** 决定权限。核心 API 也不能相信请求体中的供应商身份，必须使用经过服务端签名的上下文。

### 6.3 数据刷新

- 三个应用的页面每 5 秒刷新一次 Demo 上下文或当前详情。
- 每次业务写入成功后立即重新请求详情。
- 页面倒计时使用 API 返回的 **serverTime** 校准。
- 工作区 **revision** 变化时清理页面查询缓存并重新加载。
- React State 只保存未提交表单和 UI 展开状态。

## 7. 页面与交互设计

### 7.1 管理端寻源 Agent 页面

继续使用唯一入口 **/agents/sourcing**。为了保持“一个管理页面、一个寻源 Agent”的演示体验，不额外建设复杂后台导航。

1. 顶部标题、真实 DeepSeek 连接状态、重置 Demo 数据按钮。

- 需求编号。

- 采购物品。
- 规格与标准。
- 采购数量。
- 供应商资质。
- 交付要求。
- 报价截止时间。
- 评估策略。

采购物品变化时，其他 Select 选项从服务端模板重新加载。提交成功后生成一条新的需求并进入 Agent 寻源。

#### 四阶段详情

| 阶段 | 页面核心内容 | 主要操作 |
| --- | --- | --- |
| Agent 寻源 | 需求摘要、对话、公开执行动作、内外部候选表 | 对话调整固定选项、重新寻源、确认发布询价 |
| 等待报价 | 邀请数、注册数、查看数、提交数、最新报价、版本、竞争力和倒计时 | 一键模拟未提交报价、提前停止报价 |
| Agent 评估 | 各供应商停止时的最新报价、评估策略、Agent 运行记录、最多十条排名 | 启动或重试评估 |
| 创建 PR | 排名、中选确认、PR 摘要 | 选择一家并确认创建 PR |

报价阶段直接展示每家供应商的最新价格、交期、备注、版本号和竞争力；外部供应商提交第二版后，列表切换到最新版但历史仍保留。

候选供应商表只展示名称、内外部标识、模拟来源、匹配度、主要资质、预计交期和一句推荐或风险提示。本期不增加逐家勾选功能；采购人员可通过对话要求将候选精简为 1 至 10 家，由服务端按匹配度、交期和风险确定 Top N，确认发布后邀请该轮全部合法候选。

评估排名只展示排名、供应商名称、内外部标识、报价总价、交期、综合得分和一句结论。PR 结果只展示 PR 编号、采购物品、规格、数量、中选供应商、中选价格、交期和创建时间。

### 7.2 内部供应商 Demo

页面范围：

- **/**：固定 Mock 内部供应商身份选择。
- **/rfqs**：当前供应商的受邀询价列表。
- **/rfqs/[rfqNo]**：询价详情、附件下载和一次正式报价。

流程：

1. 选择一个预置内部供应商。
2. 服务端签发 HttpOnly 演示会话 Cookie。
3. 查看只属于该供应商的询价。
4. 打开询价时记录 **viewedAt**。
5. 提交前预览报价总价、交期和备注。
6. 二次确认后正式提交。
7. 提交成功后只显示自己的报价回执，不再显示编辑、撤回或再次提交按钮。

报价草稿可以保存在当前页面内存中，但刷新后丢失是可接受的；正式报价必须落库。

### 7.3 外部供应商 Demo

页面范围：

- **/register**：统一注册页面，展示 Mock 企业资料和简化注册表单。
- **/rfqs**：注册成功后展示当前外部供应商已经受邀的询价。
- **/rfqs/[rfqNo]**：询价详情、附件下载、首版报价、竞争力反馈和一次重新报价。

注册规则：

1. 直接访问统一注册页，不需要专属注册链接，也不校验邀请 Token。
2. 注册页默认加载唯一现场注册对象 **EXT-SUP-DEMO-004** 的 Mock 企业资料。
3. 演示人员确认企业资料并提交联系人、邮箱和密码。
4. 必填资料校验通过后，在同一次提交中直接完成注册，不经过审核、审批或激活，也不产生“待审核”状态；系统只新增外部供应商账号和联系人数据，不新增供应商主记录。
5. 密码使用 scrypt 哈希后保存。
6. 注册成功后记录 **registeredAt**，签发 HttpOnly Cookie，并跳转 **/rfqs**。
7. 询价列表根据 supplierId 查询原供应商已经存在的 RFQ 邀请，因此自动显示 **RFQ-DEMO-0002**。
8. 注册本身不要求已有 RFQ 邀请，但没有被邀请的供应商不能查看询价、下载附件或提交报价。
9. 其他外部供应商只展示预置状态，不重复演示注册。

报价规则：首版提交后立即返回 `HIGH`、`MEDIUM` 或 `LOW` 竞争力；RFQ 仍为 `OPEN` 时允许再提交一版。第二版是新历史版本而不是覆盖首版，提交后不再显示重新报价入口。

### 7.4 UI 风格与设计一致性

## 8. 核心状态机

~~~mermaid
stateDiagram-v2
    [*] --> SOURCING_RUNNING: 创建寻源需求
    SOURCING_RUNNING --> SOURCING_READY: Agent 生成合法候选
    SOURCING_READY --> SOURCING_RUNNING: 调整固定选项并重新寻源
    SOURCING_READY --> BIDDING_OPEN: 确认发布询价
    BIDDING_OPEN --> EVALUATION_PENDING: 到期或提前停止报价
    EVALUATION_PENDING --> AWARD_PENDING: Agent 评估成功
    AWARD_PENDING --> COMPLETED: 选择一家并事务性创建 PR
~~~

### 8.1 寻源需求状态

| 状态 | 页面阶段 | 含义 |
| --- | --- | --- |
| SOURCING_RUNNING | 阶段一 | Agent 首次执行、重试或重新寻源中 |
| SOURCING_READY | 阶段一 | 候选已保存，等待采购人员确认发布 |
| BIDDING_OPEN | 阶段二 | RFQ 已发布，报价进行中 |
| EVALUATION_PENDING | 阶段三 | RFQ 已关闭，已锁定各供应商最新版本，等待或正在评估 |
| AWARD_PENDING | 阶段四 | 评估已完成，等待唯一中选和 PR |
| COMPLETED | 已完成 | PR 已创建 |

Agent 失败不推进需求状态，只在 **agent_runs** 中记录失败并允许重试。

### 8.2 RFQ 状态

- **OPEN**：可查看参与进度和每家供应商的最新报价，可继续接收合法报价版本。
- **CLOSED**：不再接收报价，评估使用关闭时每家供应商的最新有效版本。

关闭原因：

- **DEADLINE**：达到服务端截止时间。
- **EARLY_STOP**：采购人员二次确认提前停止。

### 8.3 状态转换规则

| 操作 | 前置条件 | 成功结果 | 重复执行 |
| --- | --- | --- | --- |
| Agent 寻源 | SOURCING_RUNNING 或 SOURCING_READY | 保存新一轮候选并进入 SOURCING_READY | 使用新的 Agent Run，不覆盖历史 |
| 发布询价 | SOURCING_READY 且存在合法候选 | 创建 RFQ、邀请、通知，进入 BIDDING_OPEN | 返回已存在 RFQ，不重复创建 |
| 内部供应商提交报价 | RFQ OPEN、未过期、已受邀、尚无报价 | 保存唯一报价版本 | 已有报价时返回 QUOTE_ALREADY_SUBMITTED |
| 外部供应商提交报价 | RFQ OPEN、未过期、已受邀且已注册、当前版本少于 2 | 保存新版本并返回竞争力 | 已有两版时返回 QUOTE_ALREADY_SUBMITTED |
| 停止报价 | RFQ OPEN | 关闭后续报价，锁定当前版本并进入 EVALUATION_PENDING | 已关闭时幂等返回现状 |
| Agent 评估 | RFQ CLOSED 且存在最新有效报价 | 保存排名，进入 AWARD_PENDING | 已成功评估时返回现有结果 |
| 创建 PR | AWARD_PENDING 且报价属于当前排名 | 原子创建中选和 PR，进入 COMPLETED | 返回现有 PR，不重复创建 |

### 8.4 截止时间处理

本期不引入独立调度平台：

- 所有 RFQ 读取、报价提交和评估前均执行 **closeRfqIfExpired**。
- 管理端和供应商端轮询详情，倒计时归零后立即刷新。
- 报价提交使用数据库时间判断，不能相信浏览器时间。
- 即使页面倒计时没有刷新，截止后服务端也必须拒绝报价。

### 8.5 报价提交与停止的并发

提交报价和停止报价都必须在事务中先对同一 RFQ 执行行锁：

1. 报价先获得锁：若尚未到期且版本次数合法，报价成功写入，随后停止操作将该版本作为最新版本锁定。
2. 停止先获得锁：RFQ 先关闭，随后的报价返回 **RFQ_CLOSED**。

系统不得出现“RFQ 已关闭后仍新增报价版本”或“当前版本号与实际最新版本不一致”。

## 9. 数据库设计

### 9.1 数据设计原则

- 所有正式业务数据使用 PostgreSQL，不使用内存数组、JSON 文件或浏览器存储。
- 使用内部 UUID 作为关联主键，使用稳定业务编号作为三个应用共同展示和检索的编号。
- 所有业务表都包含 **workspaceId**，当前 Demo 固定属于 **DEMO-DEFAULT**。
- 金额使用 PostgreSQL **numeric(18,2)**；API 使用字符串传输，禁止 JavaScript 浮点数直接参与金额计算。
- 时间使用 **timestamptz** 保存 UTC，页面按 **Asia/Shanghai** 展示。
- 历史需求、询价、报价和 PR 保存关键字段快照，不能因模板或供应商资料调整而变化。
- 邀请数、注册数和报价数通过关联记录实时聚合，不保存容易失真的冗余计数。
- 所有写操作同时增加工作区 **revision**，供三个应用发现数据变化。

### 9.10 审计和幂等

#### workflow_events

记录创建需求、Agent 完成、发布、查看、注册、首版报价、重新报价、停止、评估和创建 PR 等业务事件，用于详情时间线和排错。

#### idempotency_records

保存高风险写操作的：

- scope。
- actor。
- idempotencyKey。
- requestHash。
- responseSnapshot。
- createdAt。

创建需求、注册、发布、报价、停止、评估、创建 PR 和重置均要求 **Idempotency-Key**。同一个 Key 和相同内容返回第一次结果；同一个 Key 携带不同内容返回冲突。

### 9.11 必须建立的数据库约束

| 约束 | 目的 |
| --- | --- |
| 业务编号在工作区内唯一 | 避免三个应用看到重号 |
| 一个需求最多一个 RFQ | 防止重复发布 |
| 一个 RFQ 对同一供应商最多一个邀请 | 防止重复通知 |
| 一个 RFQ 对同一供应商最多一条 Quote 主记录 | 按供应商统计参与和中选 |
| Quote 版本号唯一且只能为 1 或 2 | 内部一版、外部最多两版，历史不覆盖 |
| 一个 RFQ 最多一份成功评估 | 保证排名唯一 |
| 一次评估中 Quote 和 Rank 均唯一 | 防止重复和并列脏数据 |
| 一个需求最多一个 Award 和一个 PR | 保证只选一家 |
| 所有关联使用外键 | 防止孤立数据 |
| 金额大于 0，交期大于 0 | 拒绝无效报价 |

## 11. DeepSeek Agent 设计

### 11.1 调用原则

- DeepSeek 只在管理端服务端调用。
- API Key 不使用 **NEXT_PUBLIC_** 前缀，不进入浏览器包和日志。
- 使用环境变量配置 Base URL、模型、超时和重试，不把具体模型名写死在业务代码中。
- 使用官方 Chat Completions 接口的工具调用或 JSON 输出能力。
- 所有工具参数和模型 JSON 输出都经过 Zod 校验。
- 即使模型支持严格工具 Schema，服务端仍需校验参数和供应商、报价 ID 白名单。
- 不保存、不返回、不播放 **reasoning_content** 或任何隐藏思考过程。
- 页面展示的是系统生成的业务动作和最终结论。

实现依据：

- [DeepSeek Chat Completions API](https://api-docs.deepseek.com/api/create-chat-completion/)
- [DeepSeek JSON Output](https://api-docs.deepseek.com/guides/json_mode/)
- [DeepSeek Tool Calls](https://api-docs.deepseek.com/guides/tool_calls/)

### 11.2 服务端适配器

建议在管理端建立统一 **DeepSeekClient**：

- 接受结构化消息和允许的工具列表。
- 添加超时控制。
- 保存 providerRequestId、model、promptVersion 和 tokenUsage。
- 对 429、500、503 最多重试两次。
- 对 400、401、402、422 不自动重试，直接返回可诊断错误。
- JSON 为空、被截断或 Schema 不合法时返回 **AGENT_OUTPUT_INVALID**。
- 不向调用方暴露原始供应商数据库字段或报价密文。

### 11.3 阶段一：寻源 Agent

允许的业务工具：

| 工具 | 实际执行者 | 结果 |
| --- | --- | --- |
| get_sourcing_request | 服务端 | 当前结构化需求，不包含附件正文 |
| search_internal_suppliers | 服务端 SQL | 符合品类、资质和交期的内部供应商 |
| search_external_suppliers | 服务端 SQL | 带模拟来源标识的外部供应商 |
| save_candidate_suppliers | 领域服务 | 校验白名单后保存候选快照 |
| update_request_from_fixed_options | 领域服务 | 只修改 PRD 允许的固定选项 |

单轮执行流程：

1. 保存采购人员消息。
2. 创建 Agent Run。
3. 记录“读取需求”动作。
4. 服务端确定性查询内部供应商。
5. 服务端确定性查询外部供应商。
6. 将允许的候选结构化数据交给 DeepSeek。
7. DeepSeek 生成匹配说明、推荐和风险提示。
8. Zod 校验返回结构。
9. 校验所有 supplierNo 均存在于本轮查询白名单。
10. 保存候选、公开动作和 Agent 消息。
11. 将需求更新为 SOURCING_READY。

模型不能：

- 返回数据库中不存在的供应商。
- 修改固定选项之外的需求。
- 读取附件。
- 自动发布 RFQ。
- 在采购人员确认前写入邀请或通知。

### 11.4 Agent 对话修改需求

采购人员可以用自然语言提出调整，但服务端只接受可以映射为固定选项的变化。

示例：

- “交期改成 7 天内”可以映射到预置交付要求。
- “只要 ISO 9001”可以映射到预置资质。
- “增加五轴加工精度 0.002mm”如果不在固定选项中，则 Agent 说明本 Demo 暂不支持，不写入数据库。

需求发生变化后创建新 Agent Run 和新候选快照，旧候选保留历史但不能用于新 RFQ。

### 11.5 阶段二：报价期间

Agent 只允许调用 **get_quote_progress**，其输出与管理端报价进度 DTO 相同。

因此 Agent 可以读取各供应商当前最新版的金额、交期、备注、版本号和竞争力，但禁止向 Agent 提供：

- 通用 SQL 工具。
- 供应商账号、密码或会话数据。
- 旧版 quote_sealed_payloads 的密文、nonce、authTag 或密钥字段。
- 非当前 RFQ 或非当前工作区的数据。

### 11.6 阶段三：报价评估

数值评分由服务端完成，DeepSeek 只负责把已验证结果解释成简短推荐和风险提示。

预置权重：

| 策略 | 价格 | 交期 | 匹配度 | 风险与表现 |
| --- | ---: | ---: | ---: | ---: |
| 综合均衡 | 40% | 25% | 20% | 15% |
| 价格优先 | 60% | 15% | 15% | 10% |
| 交期优先 | 25% | 50% | 15% | 10% |

评分规则：

- 价格得分 = 最低有效总价 ÷ 当前总价 × 100。
- 交期得分：报价不晚于需求时为 100；超过需求时按需求天数 ÷ 报价天数 × 100。
- 匹配度使用阶段一保存的供应商匹配分。
- 风险分：低风险 100，中风险 70，高风险 30。
- 综合得分保留两位小数。
- 同分时依次按总价更低、交期更短、提交时间更早、供应商编号排序。
- 最多保存十条；不足十条时保存全部。

评估流程：

1. 校验 RFQ 已关闭，并读取每家供应商 Quote 主记录所指向的 currentVersion。
2. 从 **quote_versions** 读取全部最新有效报价；历史版本不参与排名。
3. 计算并冻结 **quoteSetHash**。
4. 创建 RUNNING 评估记录后释放数据库事务。
5. 调用 DeepSeek 生成每条报价的一句推荐和风险提示。
6. 校验返回 Quote ID、数量和文本长度。
7. 再次确认 Quote 集合和 RFQ 状态未变化。
8. 在事务中保存排名并把需求更新为 AWARD_PENDING。

DeepSeek 失败时：

- 评估记录标为 FAILED。
- 需求保持 EVALUATION_PENDING。
- 页面显示明确错误和重试按钮。
- 不用本地伪文案冒充真实 Agent 调用。

### 11.7 Agent 运行展示

页面可继续使用现有打字动画，但动画数据来自已经持久化的：

- 用户输入。
- 执行动作。
- Agent 结论。
- 业务结果。

断网或刷新后从数据库恢复，不依赖浏览器中的定时器历史。预置 Agent 对话必须标记为“Demo 初始化记录”；现场新建、重新寻源和现场评估必须真实调用 DeepSeek。

## 12. 报价版本与竞争力设计

### 12.1 提交

供应商正式确认后，核心 API：

1. 锁定 RFQ。
2. 使用数据库时间校验仍为 OPEN 且未到期。
3. 校验供应商已受邀；外部供应商还需完成注册。
4. 读取该邀请的 Quote 主记录并锁定；没有记录时创建第 1 版。
5. 内部供应商已有第 1 版则拒绝；外部供应商已有第 1 版时允许创建第 2 版，已有第 2 版则拒绝。
6. 规范化总价、交期和备注。
7. 外部供应商根据当前其他供应商最新版的平均金额和采购交期要求计算 `HIGH`、`MEDIUM` 或 `LOW`；内部供应商竞争力为 null。
8. 在 **quote_versions** 新增不可覆盖的版本，并更新 Quote.currentVersion、回执、提交时间和摘要哈希。
9. 更新 invitation.submittedAt 和工作区 revision。
10. 提交事务后返回当前报价、全部历史版本、竞争力和剩余报价机会。

正式报价不提供撤回、删除或覆盖接口；外部供应商的“重新报价”是新增第 2 版，不是修改第 1 版。

### 12.2 报价期间可见性

| 角色 | 可见 | 不可见 |
| --- | --- | --- |
| 采购人员 | 邀请、注册、查看、提交状态，以及每家供应商最新报价、版本和竞争力 | 供应商密码、技术密钥和非当前工作区数据 |
| 寻源 Agent | 当前 RFQ 聚合进度和最新报价 DTO | 通用数据库访问、账号凭证和非当前 RFQ 数据 |
| 当前供应商 | 自己的询价、报价历史、最新竞争力和剩余报价机会 | 其他供应商身份、状态和报价 |
| 其他供应商 | 自己被邀请的内容 | 当前供应商及任何其他供应商数据 |

采购端 OPEN 阶段直接从 Quote.currentVersion 关联 **quote_versions**，不需要等待停止报价。供应商端仍按签名会话和邀请关系隔离，只能读取自己的版本。

### 12.3 竞争力计算

- 没有其他有效报价时：交期符合采购要求为 `MEDIUM`，否则为 `LOW`。
- 当前总价不高于其他供应商最新版平均总价的 98%，且交期符合要求时为 `HIGH`。
- 当前总价不低于平均总价的 105%，或交期超过要求时为 `LOW`。
- 其他情况为 `MEDIUM`。
- 每次外部供应商提交新版本时重新计算，并把结果保存在该版本上；历史版本的原分析结果不回写。

竞争力只提供相对等级和简短说明，不向供应商泄露竞争对手数量、名称、金额或交期。

### 12.4 停止报价

关闭 RFQ 的单个数据库事务必须完成：

1. 锁定 RFQ 和 Demo 工作区。
2. 确认 OPEN；已关闭则幂等返回。
3. 写入 CLOSED、closedAt 和 closeReason。
4. 校验每条 Quote.currentVersion 都指向实际存在的最新版本。
5. 写入唯一 **rfq_close_events** 和关闭时 Quote 数量。
6. 把寻源需求更新为 EVALUATION_PENDING。
7. 增加工作区 revision。
8. 任一步失败时整体回滚。

停止只关闭后续报价，不改变报价内容的可见性，也不复制或重写报价明细。

### 12.5 历史表兼容与日志

- 旧数据库中的 **quote_sealed_payloads**、**revealed_quote_details**、revealedAt 和旧密钥变量仅用于迁移兼容。
- 当前报价提交、采购端展示、评估和 PR 均以 **quote_versions** 及 Quote.currentVersion 为准。
- 迁移完成后不得因旧表是否存在明细而改变 OPEN 阶段的报价可见性。
- 日志记录 Quote 编号、版本、竞争力和业务结果，不记录密码、服务凭证或历史密钥。

## 13. 事务性业务服务

### 13.1 发布询价

**publishRfq** 在一个事务中：

1. 锁定需求和工作区。
2. 校验 SOURCING_READY。
3. 校验候选来自最新成功 Agent Run。
4. 生成 RFQ。
5. 为确认范围内的每家供应商创建唯一邀请。
6. 创建模拟通知。
7. 更新需求为 BIDDING_OPEN。
8. 增加 revision。

任何一步失败都不能留下半张 RFQ 或孤立邀请。

### 13.2 注册外部供应商

**registerExternalSupplier**：

1. 读取外部 BFF 服务端固定注入的 **EXT-SUP-DEMO-004**，并校验它是数据库中已存在、类型为 EXTERNAL 且 registrationEnabled=true 的 Mock 供应商；不从浏览器请求体读取 supplierNo。
2. 锁定供应商和 Demo 工作区。
3. 校验尚未存在外部账号；若已经注册则返回 SUPPLIER_ALREADY_REGISTERED，不新增记录。
4. 校验并保存联系人、邮箱和密码哈希，创建唯一外部账号并记录 registeredAt。
5. 不插入新的 suppliers 记录，也不要求提供 RFQ 邀请或注册 Token。
6. 签发绑定原 supplierId 的演示会话。
7. 增加 revision。

注册成功后，外部供应商端按会话中的 supplierId 查询 rfq_invitations；只有已经受邀的 RFQ 才会出现在列表中。

### 13.3 中选和创建 PR

页面可分两步预览，但最终确认使用一个接口和一个事务：

1. 锁定需求。
2. 校验 AWARD_PENDING。
3. 校验 Quote 属于当前成功评估。
4. 从服务端读取评估锁定的 Quote 最新版本和供应商。
5. 创建唯一 Award。
6. 从需求和报价复制 PR 快照。
7. 创建唯一 PR。
8. 更新需求为 COMPLETED。
9. 增加 revision。

这样不会出现“已中选但 PR 创建失败”的半完成状态。

## 15. 初始化和统一重置

### 15.1 首次初始化

提供命令 **npm run demo:init** 和受保护接口 **POST /api/demo/v1/demo/initialize**。

初始化流程：

1. 获取 PostgreSQL advisory lock。
2. 检查 **DEMO-DEFAULT** 工作区。
3. 如果当前 seedVersion 已初始化，则直接返回，不修改现有演示进度。
4. 如果尚未初始化，在单个事务中创建物品、供应商、能力、账号、附件和五条完整场景。
5. 初始化预置报价主记录、版本历史和外部竞争力。
6. 执行 **assertDemoBaseline**。
7. 验证通过后提交事务并记录 seedVersion。
8. 验证失败则整体回滚。

普通启动、刷新、重新打开页面和重新部署都不能自动执行重置。

### 15.2 一键重置

管理端显示“重置 Demo 数据”按钮。用户必须在二次确认框中输入“重置 Demo 数据”后才能执行。

重置流程：

1. 获取 advisory lock 和工作区行锁。
2. 暂时拒绝新的报价、评估和 PR 写入。
3. 在一个数据库事务中删除 **DEMO-DEFAULT** 下的业务流程数据。
4. 恢复物品、供应商、能力和示例附件。
5. 重新创建五条固定需求及完整关联记录。
6. 删除 EXT-SUP-DEMO-004 的 external_supplier_accounts 记录，将其恢复为未注册；同时恢复其他固定外部供应商的预注册账号。
7. 将 RFQ-DEMO-0002 截止时间设为北京时间 `2026-09-15 23:59`。
8. 恢复阶段二预置报价、版本号和竞争力。
9. 执行完整性断言。
10. 更新 resetAt 和 revision 后提交。
11. 三个应用发现 revision 变化后刷新；旧供应商会话失效时，内部端返回身份选择页，外部端返回统一 **/register** 页。

任一步失败都整体回滚，三个应用继续看到重置前的完整数据，不允许出现半重置状态。

## 16. 跨三个项目的数据完整性

### 16.1 单一事实来源

- 三个应用不保存独立的需求、邀请、报价或注册 Mock JSON。
- 管理端核心 API 是唯一写入口，PostgreSQL 是唯一数据源。
- 供应商端页面即使有展示常量，也只能用于标签和空状态，不能代表业务状态。
- Agent 候选、邀请、报价、评估和 PR 必须由数据库关联记录产生。

### 16.2 一致性规则

| 业务结果 | 保证方式 |
| --- | --- |
| 三端显示同一需求和附件 | 同一个 requestId 和 attachmentId，通过核心 API 下载 |
| 注册不产生重复供应商 | external_supplier_accounts.supplierId 唯一 |
| 报价家数准确 | 对 Quote 主记录按 RFQ 实时 count，不把外部第二版重复计数 |
| 报价版本合法 | 内部最多一版；外部最多两版；quoteId + versionNo 唯一且 currentVersion 指向最新版 |
| 停止后三端同步 | RFQ 状态和 workspace revision 统一更新 |
| 评估只含有效报价 | 只读取每条 Quote 的 currentVersion，并把版本纳入 quoteSetHash |
| 只选一家 | awards.requestId 唯一 |
| PR 数据不可篡改 | 服务端从需求和中选 Quote 复制快照 |
| 重置同时生效 | 单事务 + revision 刷新 |

### 16.3 revision 使用

所有读取响应返回当前 revision。页面出现以下情况时重新加载：

- 后续轮询发现 revision 变化。
- 写接口返回更高 revision。
- 当前详情中的 version 过期。
- 重置后供应商会话引用的账号已不存在。

revision 只用于缓存失效，不代替数据库事务和版本检查。

## 17. 附件和通知记录

### 17.1 采购附件

- 只支持采购人员上传的需求附件。
- Agent 请求体和工具输出完全排除附件内容。
- 内部、外部供应商都通过受邀校验后的下载接口获取同一份文件。
- 下载响应设置正确文件名、MIME Type 和 **Content-Disposition: attachment**。
- 上传限制 5 MB，并限制为 PDF、图片或常见文档类型。
- Seed 附件保存 checksum；两个供应商端下载后 checksum 必须相同。

### 17.2 模拟通知

发布 RFQ 时同步生成通知记录：

- 内部供应商：RFQ_NOTICE。
- 已注册外部供应商：RFQ_NOTICE。
- 未注册外部供应商：同样为 RFQ_NOTICE，并在页面显示“待注册”。

通知只显示模拟接收地址、生成时间、发送状态和供应商注册状态，不包含注册链接或操作 Token。没有后台发送任务，也不提供“重发”功能。

## 18. 身份和基础安全

本期没有正式登录系统，但仍需保证演示数据隔离：

- 管理端固定为 BUYER_DEMO 服务身份。
- 内部供应商选择后，由内部应用服务端签发带 supplierNo、workspaceCode 和过期时间的 HMAC 签名 HttpOnly Cookie。
- 外部供应商注册后，由外部应用服务端签发相同结构的签名 Cookie。
- Cookie 使用 HttpOnly、SameSite=Lax；部署到 HTTPS 时启用 Secure。
- 核心 API 使用服务端 Bearer Token 识别来自两个供应商 BFF 的请求。
- 服务凭证、会话 Secret、DeepSeek Key 和数据库 URL 不进入浏览器；历史兼容密钥如仍配置，也只能存在于管理端服务端。
- 核心 API 根据 BFF 身份和签名上下文决定供应商，拒绝请求体伪造身份。
- 注册密码只保存 scrypt 哈希，日志中不得出现密码。
- 重置接口仅在 **DEMO_RESET_ENABLED=true** 时开放。

这不是正式生产权限模型，但足以保证现场演示时不同供应商不能互相查看数据。

## 19. 异常和恢复设计

| 场景 | 服务端处理 | 页面反馈 |
| --- | --- | --- |
| 没有候选供应商 | Agent Run 成功但候选为空，不进入可发布状态 | 提示调整固定条件后重新寻源 |
| DeepSeek 超时或 429/5xx | 有限重试，仍失败则 Agent Run FAILED | 显示失败原因和重试按钮 |
| DeepSeek 返回非法 JSON | 不保存候选或排名，不推进状态 | 显示模型输出校验失败 |
| DeepSeek 编造 Supplier/Quote ID | 白名单校验失败 | 不落库，可重试 |
| 重复发布 RFQ | 幂等返回已有 RFQ | 打开已创建询价 |
| 内部重复报价或外部第三次报价 | 类型规则、版本上限和幂等记录阻止 | 显示已提交回执或机会已用完 |
| 报价与停止并发 | RFQ 行锁决定合法先后 | 成功或明确显示报价已停止 |
| 截止后报价 | 使用数据库时间拒绝 | 显示报价已结束 |
| 无有效报价 | 不允许评估 | 提示没有有效报价 |
| 评估失败 | 保持 EVALUATION_PENDING | 可重试，不丢失已锁定的最新报价版本 |
| 重复创建 PR | 幂等返回现有 PR | 打开已创建 PR |
| 附件不存在或未受邀 | 返回 404 或 403，不泄露路径 | 显示无法下载 |
| 重置失败 | 整体回滚 | 保持原数据并显示失败 |
| 供应商页面检测到重置 | 清理失效会话和缓存 | 返回内部身份选择页或外部统一注册页 |

## 25. 部署考虑

如果三个应用部署到独立域名：

- 三个应用仍访问同一个 PostgreSQL。
- 供应商浏览器继续只访问本应用 BFF，避免向浏览器开放核心 API 凭证。
- 核心 API 只接受受信服务 Token。
- Cookie 只在各自供应商应用域名内有效。
- 外部统一注册页使用部署后的外部供应商域名，不生成按供应商或 RFQ 区分的专属链接。
- 附件保存在 PostgreSQL，因此不依赖无状态实例本地磁盘。
- DeepSeek Key、数据库 URL 和可选历史兼容密钥只配置在管理端。
- 供应商项目不配置 DATABASE_URL 或历史兼容密钥。
- 部署后分别验证三个构建、核心 API 连通和最短演示流程。

本期不把“已部署”视为“已联调”。必须使用实际部署地址走完注册、报价、停止、评估和 PR。

## 26. 主要风险和控制

| 风险 | 控制措施 |
| --- | --- |
| 现有 App.tsx 继续膨胀 | 抽出独立 sourcing feature，只保留挂载逻辑 |
| 三端复制 Mock 导致状态不一致 | 唯一核心 API + PostgreSQL |
| 采购端最新报价字段不完整或版本错乱 | 专用 DTO、currentVersion 外键语义、版本唯一约束和响应测试 |
| DeepSeek 编造供应商或报价 | 服务端查询、ID 白名单、Zod 和事务前复核 |
| DeepSeek 输出不稳定导致排名跳变 | 服务端确定性评分，模型只生成说明 |
| 提前停止与报价并发 | RFQ 行锁、Quote 行锁和单事务状态转换 |
| 外部注册产生重复供应商 | supplierId 唯一，只新增账号 |
| 重置破坏三个应用一致性 | 工作区写锁、单事务、revision 和基线断言 |
| 现场 RFQ 已过期 | 报价进行中的固定 RFQ 截止到北京时间 `2026-09-15 23:59`，演示前检查其状态 |
| Secret 泄漏到浏览器 | 全部服务端变量，禁止 NEXT_PUBLIC_，构建产物检查 |
| DeepSeek 临时不可用 | 明确失败、可重试、使用预置历史继续说明 |
| 三个项目视觉逐渐漂移 | 共享 haitian-ui-theme，并纳入桌面和移动端截图验收 |
| 现有用户改动被覆盖 | 实施前记录工作区状态，禁止 reset 和无关文件提交 |

## 27. 完成定义

同时满足以下条件才算本方案实施完成：

1. 三个 Next.js 应用可以独立启动并完成跨应用流程。
2. 现有管理端非寻源页面和另外五个 Agent 没有回归。
3. 所有正式业务状态都来自 PostgreSQL。
4. 五条固定需求及其前序数据完整，重复初始化不重复。
5. 一键重置能同时恢复三个应用的统一基线。
6. Agent 现场操作真实调用 DeepSeek，输出经过结构校验。
7. Agent 不编造供应商，不读取采购附件，不展示隐藏思考过程。
8. 报价进行中，采购人员和 Agent 可以看到每家供应商最新报价、版本和竞争力，且不暴露账号凭证或其他工作区数据。
9. 内部供应商只能提交一版；外部供应商最多两版并在每次提交后获得竞争力，供应商只能读取自己的数据。
10. 提前停止和截止关闭都只停止后续报价，关闭后不能再新增版本。
11. 评估只包含每家供应商停止时的最新有效版本，排名可重复且最多十条。
12. 只允许一家中选，PR 与中选报价的供应商、金额和交期一致。
13. 刷新、重启和三个应用切换后状态不丢失、不倒退。
14. 单元、集成、API 合约和核心 Playwright E2E 全部通过。
15. 三个项目的 typecheck 和 build 全部通过。
16. 管理端、内部供应商端和外部供应商端的主题、字体、圆角、间距、状态和反馈与现有 haitian 视觉体系一致。
